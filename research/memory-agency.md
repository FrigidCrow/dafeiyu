# 大肥鱼：人格、记忆、主动性与 MaiBot 基底研究

核查日期：2026-10-25（Asia/Tokyo）。范围：一人使用，先 Mac 运行，稳定后迁服务器；普通 QQ 好友私聊并主动找用户；有自己感兴趣的内容，能浏览 B 站；人能管理记忆。

证据层级：本文阅读了官方文档、GitHub 指定版本源码及原始论文，未安装运行这些系统，未做 QQ 实号、Mac 适配器或 B 站访问实测。产品体验判断与建议均为研究推断。

## 结论

1. **值得把 MaiBot（麦麦）列为优先原型基底。** 用户最重视人格连续、日常聊天与主动找自己，MaiBot 的内置人格、聊天决策、长期记忆及主动任务入口，比通用机器人框架更直接覆盖这些需求。建议保留它的人格和 A_Memorix 记忆主线，自己写一个“生活与 B 站”插件，负责真实经历、兴趣、日程与是否打扰的约束。
2. **不要再给 MaiBot 并排接一套 Mem0 或 Letta 作为第二记忆真相。** 这些项目适合借鉴或在完全自建时选择；和 MaiBot 同时负责用户画像、事实更新、摘要、删除，会增加冲突。一个系统必须明确谁持有权威记录、谁只是检索缓存。
3. **活人感应来自可追溯经历、稳定偏好、承诺兑现和合适的发言时机。** 不应主要依赖随机延迟、随机情绪、频繁问候或把“自主行为”写进 prompt。模型一次次声称刷了视频，不能替代浏览工具实际成功。
4. **人工管理不止是一个删除按钮。** 至少要区分纠正、锁定、不再检索、彻底清除，并处理派生摘要、人物画像、向量、缓存、历史消息与备份。MaiBot 已有很好的管理基础，但尚不能据文档直接承诺完全遗忘。

## MaiBot 当前核实到什么

官方 GitHub 最新正式发布为 **v1.3.15**，发布时间 **2026-10-23 17:49:35 UTC**，主项目许可证 GPL-3.0。公开文档部分于 2026-10-25 更新；文档会领先或落后于固定版本，因此实施时必须固定主程序、插件 SDK 和 QQ 适配器版本。[发布记录](https://github.com/Mai-with-u/MaiBot/releases/tag/v1.3.15)

### 私聊与主动性

当前文档支持按用户 ID 获取或创建私聊流。插件的 `ctx.maisaka.proactive.trigger()` 可以把意图交给 Planner，由现有人格、记忆与上下文决定是否回复、如何表达；`context.append()` 可追加带来源的外部经历。固定版本源码也存在 `_cap_maisaka_proactive_trigger`，并调用 `runtime.enqueue_proactive_task`。这意味着生活插件可以提交“刚发现一个值得分享的视频”事件，复用主体的说话方式。它本身不是“全天自主生活”功能，仍需要生活插件提供触发、状态与预算。[官方插件 API](https://docs.mai-mai.org/plugin/api-reference)

源码定位（已读 v1.3.15）：

- [主动任务与上下文](https://github.com/Mai-with-u/MaiBot/blob/v1.3.15/src/plugin_runtime/capabilities/core.py)：`_cap_maisaka_proactive_trigger` 从约 331 行开始，检查目标聊天流，入队并返回执行请求结果；不能把入队成功当 QQ 已送达。
- [创建/查找私聊流](https://github.com/Mai-with-u/MaiBot/blob/v1.3.15/src/plugin_runtime/capabilities/data.py)：`_cap_chat_open_session` 从约 313 行开始，支持 account_id/scope 路由。

### 人格与人工管理记忆

MaiBot 的人格配置区分“是谁”“何时参与”“怎样说话”。这是合适的结构：身份和底线比较稳定，表达可以适应上下文。它的默认示例有群聊文化色彩，需要改成一对一陪伴的风格，不能只换名字而保留群聊抢话习惯。[人格与行为配置](https://docs.mai-mai.org/manual/configuration/bot-config)

WebUI 提供文字记忆、人物画像、记忆变动时间线、导入、纠错、删除恢复等。可人工覆盖人物画像；**普通段落目前没有任意文本编辑入口**，官方建议删错误来源后重导入或用反馈纠错。删除后默认进入可恢复状态，不能等同物理擦除。数据主要在本地，但摘要、画像、向量化会调用配置的模型服务。[记忆管理](https://docs.mai-mai.org/manual/webui/memory-management)

A_Memorix 是内置子系统，长期记忆默认关闭；启用前应配置 embedding，否则进入只有稀疏检索的降级状态。存储包括 SQLite 元数据、向量、图谱、Episode、画像、事实账本和后台队列。默认以聊天流隔离，跨聊天共享是独立配置。一人专用初版只允许目标用户私聊，保持跨流共享关闭。[A_Memorix 配置](https://docs.mai-mai.org/manual/configuration/amemorix-config)

### 可扩展性与源码边界

固定版本 A_Memorix 的 [README](https://github.com/Mai-with-u/MaiBot/blob/v1.3.15/src/A_memorix/README.md) 列出 `ingest_text`、`ingest_summary`、`memory_profile_admin`、`memory_delete_admin` 等管理入口，并说明由宿主的 React 页面和 `/api/webui/memory/*` 承接。其内部默认许可是 AGPL-3.0，针对 MaiBot 有 GPL 额外授权；不要直接把该模块拷进另一个闭源工程而假定许可相同。

建议扩展现有入口，而不是直接修改数据库：

| 责任 | 当前源码位置 | 对项目的用法 |
|---|---|---|
| 记忆统一入口 | `src/A_memorix/core/runtime/sdk_memory_kernel.py`、`src/A_memorix/host_service.py` | 外部经历写入经宿主服务，使用稳定 external_id 去重 |
| 人物覆盖 | `src/A_memorix/core/runtime/services/profile_admin_service.py` | `set_override`/`delete_override` 支持人工权威描述，保留修改人和来源 |
| 删除协调 | `src/A_memorix/core/runtime/services/delete_admin_service.py` | 预览、执行、恢复、purge，并协调向量清理 outbox |
| 向量删除 | `src/A_memorix/core/runtime/services/vector_delete_service.py` | 区分段落、实体、关系及双向量池，不能只删一行文本 |
| 管理 UI 后端 | `src/webui/routers/memory.py` | 已有画像 override、memory/freeze、删除、导入等路由 |
| 管理 UI 前端 | `dashboard/src/components/memory/` | 可以在现有编辑/删除/维护界面增强，不另造不一致的管理后台 |

已读代码并非完整审计。现有插件文档明确公开主动任务和上下文 API，但没有证明任意第三方插件可直接调用所有 A_Memorix 内部管理工具。**实施前需要做小型接口验证**：通过受支持宿主能力接入；若缺少正式接口，补一个窄的宿主桥接能力，并给出兼容性约束。不要在插件进程直接导入宿主内部对象、直写数据库，或硬编码 WebUI 登录令牌。

### 相对 AstrBot 的取舍

| 方面 | MaiBot 对本项目的价值 | 需要接受的代价 |
|---|---|---|
| 活人感 | 人格、时机决策、表达学习、Planner 已在主体内 | 主体的聊天策略更有主见，需要调节一对一风格 |
| 记忆 | 同一内置系统含事件、画像与管理 UI | 配置很多，纠错/彻底遗忘需专项验证 |
| 插件 | 可提交主动意图，保持人格一致 | Host/Runner IPC 与 SDK 在演进；旧 Action 正迁到 Tool |
| 资源 | 文字聊天可先用一个 LLM 和一个服务商 | 完整记忆需 embedding，看图需 VLM；摘要/学习/反思都是额外调用 |
| Mac→服务器 | 主程序官方支持 macOS/Linux，已有数据导入导出 | QQ客户端适配是独立问题；迁移要连同版本、配置、状态与重连一起验收 |

模型要求来自[官方模型配置](https://docs.mai-mai.org/manual/configuration/model-config)，插件架构来自[插件开发指南](https://docs.mai-mai.org/plugin/)。不能据“最低 2GB 可用内存”推断完整多模态后台浏览也只需要 2GB，更不能把它当性能实测。

实质性维护信号：v1.3.15 的 A_Memorix README 还出现旧 `config/a_memorix.toml`，而最新正式配置文档说明已统一到 `config/bot_config.toml` 的 `[a_memorix]`。发布记录也显示私聊频率配置刚发生调整。**因此建议固定版本，使用该版本生成的配置，并写少量兼容适配。** 若用户更看重完全自定的产品行为、通用接入和长期维护，可转向 AstrBot 统一插件；这会把人格决策、记忆管理与生活循环的更多工作交给自己。

## 研究依据与能借鉴到什么

**Generative Agents** 在模拟小镇中将观察、记忆、反思和计划组合，消融实验表明这些部分对行为可信度有贡献。它支持“连续经历比单一人设提示词更有价值”的设计方向；其模拟场景不能证明 QQ 陪伴长期好用，更不能证明意识或真实情感。[原始论文，2023](https://arxiv.org/abs/2304.03442)

**MemGPT / Letta** 的启发是分开“总在上下文里的核心内容”和“按需检索的外部记忆”。Letta V1 的 memory blocks 支持只读块、人工修改和删除，但更新是整块替换，并发最后写入会覆盖前值；该 API 当前已放在 legacy 文档区。现行 Agent SDK 改为 Git 支持的 MemFS，system 文件常驻上下文，其他文件按需读取，并有后台记忆整理。迁移和可审计值得借鉴，但仅从 Git 删除文件不会自动清理历史提交。[MemGPT 论文](https://arxiv.org/abs/2310.08560)、[V1 memory blocks](https://docs.letta.com/v1-sdk/memory/memory-blocks)、[当前 Agent SDK memory](https://docs.letta.com/agent-sdk/memory)

**Mem0** 是可嵌入的记忆层，并提供增删改查。其 OSS 示例默认仍使用云端模型做抽取和嵌入；“开源/本地存储”不等于“所有内容不出机器”。OSS 的管理 UI 还需要自己实现；平台版 UI 不能自动算作 OSS 能力。它适合完全自建内核时减轻抽取与检索工作，不负责人格、QQ 或生活调度。[OSS quickstart](https://docs.mem0.ai/open-source/python-quickstart)、[更新 API](https://docs.mem0.ai/core-concepts/memory-operations/update)、[删除 API](https://docs.mem0.ai/core-concepts/memory-operations/delete)

**LongMemEval** 把长期记忆拆成信息提取、跨会话推理、时间推理、知识更新、拒绝无依据回答五类。这比只问“记得我名字吗”更适合验收。[原始论文，2024](https://arxiv.org/abs/2410.10813)

## 推荐人格与记忆结构（工程设计建议）

下面是应用层责任划分，不是要求另建一套与 A_Memorix 竞争的记忆服务。

| 层 | 内容 | 修改方式 |
|---|---|---|
| 稳定人格核 | 身份、称呼、价值取向、对话边界、标志性表达 | 用户编辑并版本化；日常网页或聊天不能自行重写 |
| 逐渐形成的偏好 | 喜欢的分区/UP主、讨厌的内容、对话习惯 | 基于多次经历形成候选；记录支持来源，允许修正 |
| 当下状态 | 当前在看什么、最近关注什么、是否忙、近期未完话题 | 有到期时间；关机/重启后根据真实记录恢复，不编造离线生活 |
| 关于用户的事实 | 称呼、偏好、明确日程等 | A_Memorix 保存，区分用户明示与模型推断；冲突看来源与时间 |
| 共同经历 | 昨天分享的视频、用户反应、讨论过的观点 | 记录事件及来源，摘要是派生物 |
| 承诺与计划 | “明晚再问问你”“下一次找这个UP的新作” | 独立任务状态：待办/已完成/取消/过期，避免只写自然语言忘执行 |

生活插件可以维护浏览任务、调度游标、发送去重键和预算等**业务运行状态**，这不构成第二个人格记忆库。重要经历应回写现有记忆系统，主体通过一个入口读取与解释。B站网页正文属于外部资料，不能当作用户身份事实或人格指令。

建议每条长期记忆的可管理信息包括：ID、类型、主体、内容、来源消息或URL、发生时间、入库时间、有效期、可信状态、人工锁定、版本、派生来源、替代关系。置信度数值不能单独把推断变成事实。

人工管理的四种动作应明确展示：

- **纠正**：保留更正关系，旧内容停止参与当前事实回答；重建受影响画像和检索内容。
- **锁定**：人工确定内容不能被普通抽取覆盖；有冲突时显示待处理，不静默改写。
- **不再使用**：从检索和上下文剔除，但仍允许回收恢复。
- **彻底忘记**：清除原始记录与派生摘要/画像/向量/缓存，并明确原始聊天、日志、备份是否也覆盖；无法清除的范围如实列出。

删除验收尤其要检查：当前对话是否仍带着旧内容；后台正在运行的总结任务是否在删除后把记忆写回来；从备份恢复后是否重新出现。数据库已经删除不代表生成上下文已经刷新。

## 主动生活循环（工程设计建议）

采用事件和低频调度，不让大模型每分钟空转：

1. 触发来自用户消息、关注内容更新、约定时间、已选择的空闲浏览时段。
2. 先用普通代码检查作息、预算、冷却、重复内容、用户最近是否忽略多次消息。
3. 需要时才让主体在“继续聊、刷一点、记下来稍后聊、现在保持安静”中选。
4. 浏览成功后生成带证据的经历：BV号/URL、获取时间、字幕或画面范围、工具成功/失败、自己的观点与不确定性。
5. 值得分享时交给同一个 Planner 和 Replyer，结合上次话题自然表达；发送回执后再标记已分享。
6. 每日或积累到足够新信息才做摘要/反思；不能把模型想象的经历再当新证据循环强化。

第一版可设可调的安静时段、每日主动消息上限、同类话题冷却、连续无回应退避。数值是用户体验参数，应在一周试用后调整，论文没有证明统一最佳值。“两条普通问候”往往不及“一条和昨天共同话题相关的新发现”。

真实性要求：只拿到标题就说“看到一个标题”，读到字幕就说“看了字幕内容”，获取并分析画面后才描述画面。没有成功的浏览记录不能声称自己刷过；离线期间不会自动拥有真实新经历。

## Mac 原型与迁移建议

先验证三个闭环，随后再加复杂行为：

1. 普通 QQ 私聊双向收发，重启后仍认识同一用户；无用户新消息时能受控发出一条主动消息。
2. 记住一个偏好→跨会话使用→人工纠正→按新值回复→删除后不再检索；验证用户能看懂管理页面。
3. 真实读一条 B 站内容→形成有证据经历→结合旧话题主动分享→第二天能接着聊。

通过后再一周试养；此时再决定是否要桌宠、语音、更多网站。主程序支持 macOS 不等于 QQ 普通账号接入已在这台 Mac 验证，不能略过连接器测试。

MaiBot 的 WebUI 已提供 config/data 及可选 plugins/logs 的数据包导出导入，包内记录程序版本。迁服务器应先停任务并备份，在相同版本恢复，再测试记忆检索、任务去重、QQ重连、主动消息和时区；服务端和 Mac 不能同时以同一身份重复执行生活任务。[数据迁移](https://docs.mai-mai.org/manual/webui/data-management)

## 有意义的验收

建议准备小型固定场景，而不是只盯模型觉得自己“有活人感”：

| 场景 | 预期 |
|---|---|
| 相隔一天再提同一UP主 | 正确接回共同经历，不套一段通用问候 |
| 用户从喜欢游戏A改为不想看 | 最新明确偏好生效，历史经历仍能区分过去与现在 |
| 问从未告诉过的生日 | 承认不知道，不把猜测写入记忆 |
| 人工删某段经历 | 新对话、检索、人物摘要不再使用，后台不复活 |
| 浏览失败/字幕缺失 | 说明访问失败/只获取到的范围，不伪造观点依据 |
| 用户连续未回复 | 自动减少打扰；不是越来越焦虑地发消息 |
| 同一事件重复到达或服务重启 | 不重复分享、不重复承诺 |
| 用户提问与浏览任务并发 | 优先响应用户，浏览状态不覆盖正在聊的话题 |

一周人工反馈重点：是否愿意继续聊、是否感觉记得共同经历、主动消息是否相关、是否讨厌被打扰。加上客观记录：正确更正率、无依据经历次数、删除后再出现次数、重复推送次数、每日调用成本与错误率。原型通过只代表这一组场景通过，不能宣称“已实现真正数字生命”。
