# 长期记忆：生命周期、人工控制、Token 成本与验收

研究日期：2026-10-26（Asia/Tokyo）。对象：DSH 统一陪伴插件中的中文一对一长期记忆。本文引用原始论文、作者仓库、DeepSeek 与 SQLite 官方资料；“建议”属于本项目设计判断。未运行产品、调用付费模型、登录账户或执行 benchmark，没有本项目性能/成本实测。

## 1. 核心结论

**应采用“可追溯原证据 + 有版本的结构化记忆 + 小段近期上下文 + 按需检索”的混合方案。** 摘要用于导航和省略，不能成为唯一事实源；向量用于找候选，不能决定一条记忆现在是否允许使用。LongMemEval 原论文在其设定中发现，用摘要或抽取事实完全替代原回合会损失信息，效果还随读者模型和预算变化。因此，不把某论文的最优 top-k、窗口或节省比例直接套到中文 DeepSeek 陪伴上。[LongMemEval v2，2025-03-04，§5.2–5.4](https://arxiv.org/html/2410.10813v2)

**人工修订必须改变后续行为，而不仅是列表上的文字。** 需要同时治理原始来源、摘要、画像、索引、当前 Session、在途抽取、待发消息和备份恢复。删除一条向量不足以防止它从旧日志再次出现；“不再使用”和“所有副本物理擦除”也不是同一承诺。SQLite 官方甚至明确指出，普通 `secure_delete` 不能保证清掉 FTS 等虚表影子表的全部取证痕迹。[SQLite secure_delete](https://www.sqlite.org/pragma.html#pragma_secure_delete)

**先分别算清 Token、金额和上下文空间，再谈节省。** 记忆构建、改写、查询扩展、重排、后台反思和失败重试都可能消耗模型调用；缓存命中仍占输入上下文，且不是长期记忆。DeepSeek 的余额接口返回金额，不提供固定的“剩余 Token 数”。[官方缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)、[官方余额接口](https://api-docs.deepseek.com/api/get-user-balance/)

## 2. 原始研究告诉我们什么，不能推出什么

| 一手来源及版本 | 可采用的发现/方法 | 对本项目的限制 |
|---|---|---|
| [LongMemEval](https://arxiv.org/abs/2410.10813v2)，ICLR 2025，v2 2025-03-04 | 500 道问题覆盖信息抽取、多会话推理、时间推理、更新和拒答；分开索引、检索、读取分析 | 不是中文情感陪伴体验测试，也不替代删除、重启和发送竞态验收 |
| [LoCoMo](https://aclanthology.org/2024.acl-long.747/)，ACL 2024 | 长对话、时间事件关系、QA、事件总结与多模态对话；数据由模型生成并经人工核验编辑 | 不能把合成数据表现等同于真实主人长期相处；这里不照搬不同论文用 tokenizer 得到的长度数字 |
| [LOCOMO-CONV](https://arxiv.org/abs/2609.03467v2)，预印本 v2 2026-09-22 | 普通对话、隐含提示、反事实和组合线索能暴露 QA 式探针遗漏的召回问题；检索好不必然答得好 | 属于较新预印本、继承 LoCoMo 来源；适合补充设计，不作为唯一标准 |
| [Mem0](https://arxiv.org/html/2504.19413v1)，预印本 2025-04-28 | 抽取与更新分开，候选与相似记忆比较后选择新增、更新、删除或不操作 | 作者实现和评测不证明本项目能同幅省钱；模型判断 DELETE 不应直接授权删除人工锁定事实或原始证据 |
| [MemoryBank](https://arxiv.org/abs/2305.10250v3)，v3 2023-05-21 | 将时间、重要性和反复使用纳入记忆强化/衰减设计 | 模拟遗忘是产品策略，不是用户同意的数据擦除；“多久没聊就忘记主人重要事实”没有由此得到正当性 |
| [Generative Agents](https://arxiv.org/abs/2304.03442v2)，v2 2023-08-06 | 经历记录、检索、反思与计划协同形成连贯行为 | 模拟环境中的可信行为不证明真实情感；反思是派生推断，不能升级成未经证实的事实 |
| [Lost in the Middle](https://arxiv.org/abs/2307.03172v3)，v3 2023-11-20 | 其测试中的长上下文效果受证据位置影响 | 不推断当下每个模型同样退化；本项目应做位置、长度和干扰项测试，而非只比较标称窗口 |
| [On Faithfulness and Factuality in Abstractive Summarization](https://aclanthology.org/2020.acl-main.173/)，ACL 2020 | 摘要可能产生不被原文支持的内容；流畅度和传统相似指标不足以保证忠实 | 论文不是当代 DeepSeek 的错误率测量；用于要求来源核验和摘要审计，不引用旧错误率预测本产品 |

这些研究支持拆分问题、设计对照实验；没有一篇证明“装好某记忆库就永远不会忘、不会误记、不会泄漏”。

## 3. 先明确“这是什么记忆”

以下是适合本项目的领域划分建议。每条内容至少带 `fish_id / relationship_id / subject_id / source_ids / event_time / recorded_at / type / epistemic_status / revision / status`；时间不明确时保存原表达与不确定范围，不擅自补精确日期。

| 类型 | 示例 | 规则 |
|---|---|---|
| 人工锁定的人格与关系约定 | “不要用某昵称称呼我”；主人设定的稳定人格 | 只能通过明确管理动作改写；模型反思无权覆盖 |
| 用户明确陈述 | “我目前住在大阪” | 标为“用户自述”，不冒充外部已验证事实；区分当前有效与历史状态 |
| 系统有证据的事件 | 某条 QQ 消息收到、某请求实际返回、平台接受发送 | 绑定事件 ID 和状态。候选文本已在 Agent 日志，不代表已对主人说过；发送未知不记成确定已送达 |
| 关系经历 | “上周一起讨论了那段音乐”；主人对某次分享的回应 | 保存参与者、发生时间、具体对话与已发消息来源；不要凭模型脑补双方共同经历 |
| 临时状态 | “我今天有点累” | 有时间范围；不能升格为长期性格、健康诊断或永久关系判断 |
| 推断/反思 | “可能更喜欢安静的交流方式” | 显式标注推断及证据；可撤销、可过期，必要时询问，不能因重复自我引用变成事实 |
| B站外部知识 | 视频中的观点、字幕、事实主张 | 单独的外部资料域，保留作者/URL/取得时间/覆盖范围；不成为用户的观点 |
| 鱼的观察活动 | “读取了这段视频字幕，并形成某个看法” | 这是系统有证据的观察，不等于看完视频，更不等于主人接受该看法 |

**中文陪伴尤其要保留否定、转述、语气和时间。** “我朋友喜欢猫”不能写成“主人喜欢猫”；“以前喜欢，最近不喜欢”不能按同义句合并；“要是我搬去东京……”是反事实，不是搬家事件；“算了随便吧”可能是当时回应，不能自动变成长期偏好。这里的提取规则是设计要求，需要中文标注样例验证。

原始证据可以支持多种派生记忆，但派生摘要不能反过来作为唯一“独立新证据”。同一消息在 QQ 重投、Session、摘要中出现三次，只算同一个来源，不人为提高置信度。B站重复转载也不自动算多个独立来源。

## 4. 生命周期：从一次对话到可治理的长期记忆

推荐流程：`记录来源 → 候选抽取 → 约束核验/去重/冲突处理 → 提交修订 → 建索引 → 检索时再验状态 → 组装上下文 → 用后反馈与按需归档`。Mem0 的分阶段抽取/更新可以借鉴，但本项目把人类约束和确定性检查放在模型决策之外。[Mem0 §2.1](https://arxiv.org/html/2504.19413v1)

1. **来源先落稳。** 来源 ID 按平台事件去重，记录说话者、谈论主体、时间、原文或可定位片段、读取权限。仅把已经可持续引用的来源交给抽取。不要依赖 UI 气泡作为唯一证据。
2. **增量抽取，不每条消息重读一生。** 普通闲聊可批量提候选；明确“记住/改正/别再记”的管理动作立即处理。抽取窗口带少量必要上下文，但输出必须指向本批真实来源；记忆吞吐、尚未处理数量和最长延迟要可见。
3. **先检查约束，再做模型合并。** 校验关系/主体、来源是否撤销、否定/引用、人工锁定、任务代次和字段完整性。模型可以建议 `ADD / REVISE / LINK / CONFLICT / NOOP`，不能越过这些校验任意改库。
4. **去重与变化分开。** 完全相同来源直接幂等；同一事实的等价表达可合并来源；不同日期的真实重复活动保留为不同经历。语义近似只是候选，不是“同一个事实”的证明。
5. **更新保留时间性。** 用 `valid_from / valid_to` 表示何时成立，用 `recorded_at` 表示何时得知。搬家通常关闭旧住址有效区间、创建新版本；“你当时住哪里”仍可用历史版本。纠错与自然变化必须区分；人类说旧值根本错误时标为撤销，而非有效历史。
6. **冲突不按最后到达者一律覆盖。** 新抓取的旧消息、引用别人、模型推断，都可能比人工确认的当前值晚到。冲突应保留待核状态；明确人工更正优先。跨时区和相对日期的解析要带原始时间依据。
7. **摘要可重建、可失效。** 每段摘要/画像存来源集合与版本依赖；抽取结果保留关键原句指针，必要时回到原文。避免不断“摘要的摘要”而切断来源；人工更正后撤销相关摘要，重建时只用当前有效来源。摘要压缩率和原文支持率分开评估。[摘要忠实性研究](https://aclanthology.org/2020.acl-main.173/)
8. **检索在入口和出口都过滤。** 先限关系、主体、允许范围和时间；关键词/语义检索只返回候选 ID。真正注入前，再查权威库的最新版本、状态、撤销规则和预算。缓存命中的旧文本也不能绕过这次检查。
9. **召回由任务驱动。** 日期、昵称、作品名等精确线索与语义线索并用；时间问题先解析时间范围。跨经历问题允许补取证据，没证据时保留不确定。避免只凭“最相似”召回一堆与当前关心无关的旧隐私；自然聊天也不应每次炫耀记忆。对隐含提示的测试有必要，因为明确问答不覆盖真实聊天的召回困难。[LOCOMO-CONV v2](https://arxiv.org/abs/2609.03467v2)
10. **衰减调召回，不偷偷删重要关系事实。** 近期状态可过期，低价值观察可冷存档；人工固定项、未完成约定和纠错记录不因没被提起就自动删除。访问频率可帮助排序，但不能把系统自己反复提到某事算成人类强化。[MemoryBank 方法背景](https://arxiv.org/abs/2305.10250v3)

状态操作应当有明确产品语义：

| 操作 | 存储内容 | 后续行为 | 可逆性 |
|---|---|---|---|
| 冷存档 | 保留内容、来源和索引策略标记 | 默认不进日常召回；明确历史查询可按政策读取，UI 要说明 | 可恢复 |
| 停用/禁止使用 | 保留内容供人工查看，标记不可用于生成/抽取 | 从模型上下文、派生任务和主动分享中排除 | 可人工重新启用 |
| 修订 | 写新版本，旧版本保留审计或按策略清除 | 新值下轮生效；旧派生材料失效 | 可按明确版本回滚，不自动覆盖人工锁 |
| 逻辑遗忘/来源撤销 | 删除或屏蔽活动内容，同时保留最小撤销规则 | 后续受控检索/重建不得从被撤销来源再学习 | 只能明确解除撤销，不因重建索引自动恢复 |
| 硬删除指定应用范围 | 清理选定原文、派生数据、索引及应用管理的副本 | 返回已清理/未能清理/不在控制内的范围 | 通常不可逆；备份是否保留必须另列 |

“冷存档”不等于“不要再用”；“移到备份目录”不等于硬删除；“忘掉某件事”也不应暗中把敏感正文复制到永久审计日志里。

## 5. 人工改删后，如何不被旧资料重新学回

建议采用一笔产品库事务与两道执行门禁，具体实现仍待开发：

- 事务内提交修订/撤销、递增 `memory_epoch`、更新最小 `erasure_rule`，失效所有依赖摘要/画像/索引，取消尚未发送的旧候选。审计只保留必要对象 ID、操作人、时间和范围，硬删除不保留被删敏感正文。
- 每次抽取、摘要、检索、重建、反思都携带来源版本和 epoch；提交前再校验。已在外面计算的旧任务不能在删除之后把旧值写回来。
- 每次模型请求前重新过滤；生成结束及实际发送前再检查。删除发生在云端生成过程中，取消本地等待并不证明远端已停止；过期候选应被丢弃，且不得当作已经说过的事实。
- 若当前 DSH Session/压缩摘要仍含被禁内容，轮换执行 Session，用筛选后的权威上下文恢复，同一 `fish_id / relationship_id` 保持不变。旧 Schedule 会恢复旧 Session，故还需会话代次门禁、删除/重建任务和对账，而不只是换一个 Session ID。[DSH Schedule 固定源码语义](https://github.com/deepseek-ai/deepseek-harness/blob/22ddee3792402c3e70ec5f86a63c3e3e895a2f60/docs/subsystems/schedule.md#L440-L480)
- 从备份恢复时，先应用最新撤销清单，再允许重建索引、抽取或发送。不能恢复一个旧备份后顺手把撤销清单也回滚。备份缺少必要撤销版本时进入待人工处理状态。

**防再学习的保证必须有范围。** 使用稳定来源 ID、派生依赖和任务代次，可阻止已知旧来源重放；但若用户以后用新措辞重新提供信息，系统不能在完全不保留识别线索的同时保证识别所有语义等价内容。UI 应让用户区分“撤销这几个来源”和“今后不记某一类信息”，后者保存必要的类别/关系策略，不偷偷保留一份被删正文。误匹配与漏匹配都要测试。

硬删除回执至少分列：产品库活动数据、历史修订、摘要/全文/向量索引、媒体缓存、DSH Session 日志、运行中请求、应用备份、系统/第三方备份。产品不能越权宣称已经删除它没有管理权限的宿主日志、云端请求缓存、QQ 历史、B站内容或操作系统备份。官方缓存文档说明服务端缓存会自动清理，但这不是产品已验证的按记忆逐条删除接口。[DeepSeek 缓存说明](https://api-docs.deepseek.com/guides/kv_cache/)

本地 SQLite 还要处理 WAL、FTS 影子表和备份：不是只对主表 `DELETE` 后就宣传取证级擦除。使用合适的检查点、索引清理/重建与一致性备份接口，并按目标范围验证；本报告不承诺底层 SSD 或第三方副本的物理擦除。[SQLite WAL](https://www.sqlite.org/wal.html)、[secure_delete 限制](https://www.sqlite.org/pragma.html#pragma_secure_delete)、[官方备份 API](https://www.sqlite.org/backup.html)

## 6. Token 和钱：需要分项核算

### 6.1 四种“剩余”不能混显示

| UI 项目 | 它实际上是什么 | 能否由官方余额接口直接得到 |
|---|---|---|
| 账户余额 | DeepSeek 当前可用金额，含赠送与充值分项，带币种 | 可以；`GET /user/balance` 返回 `balance_infos` 与 `is_available`，需要用户授权配置凭据；本次未调用 |
| 产品剩余预算 | 用户给这条鱼设定的日/月金额或 Token 限额，减已确认与已预留消耗 | 不可以；由本地产品账本维护，并处理请求中、失败和未知账单 |
| 本轮剩余上下文空间 | 模型上下文上限减本轮输入、输出/推理预留和协议开销的估算 | 不可以；取决于所用模型和实际请求。不要把它当账户额度 |
| 预计还能聊多久/多少 Token | 依据模型、输入输出比例、缓存比例、后台任务和时段的情景估计 | 没有固定值；只能给假设和范围，不能伪装为官方 `remaining_tokens` |

余额接口的确切字段是 `currency / total_balance / granted_balance / topped_up_balance`，没有“剩余 Token”字段。[DeepSeek 官方余额文档](https://api-docs.deepseek.com/api/get-user-balance/)

### 6.2 全生命周期成本公式

为每个阶段记录独立调用：`chat / extraction / consolidation / reflection / query_expand / rerank / observation / evaluation`。一次生活活动可能产生多次模型请求，聊天回合数不能直接替代请求数。

```text
模型费 = Σ每次请求 [(H × 缓存命中输入单价 + M × 未命中输入单价
                   + O × 输出单价) / 1,000,000]
总成本 = 模型费 + embedding费用 + 独立rerank费用 + 外部读取/搜索费用
       + 存储/运行成本
```

其中 H+M 是输入 Token，O 用 API 计费口径的 completion Token；`reasoning_tokens` 是 completion 的细分，不应再加一次造成双计。`total_tokens` 不能直接乘一个单价。每条账目保留模型标识、时间、阶段、请求/活动 ID、usage、价目版本和金额估算；流式响应中断未取得最终 usage 时记为未知，而不是零成本。当前官方流式文档说明最终 chunk 携带整次统计；实现时按实际供应商格式处理，不照抄别家 usage-only chunk 假设。[Chat Completions usage 与流式规范](https://api-docs.deepseek.com/api/create-chat-completion/)

Embedding 可能用于新内容、修改后的重建、每次查询和模型升级全量重嵌入；云端按所选供应商费率算，本地也有计算和存储成本。rerank 若是 LLM，记入模型阶段；若是专门模型/API，按其单位另记，避免重复计费。本次未核实 DeepSeek 官方有可直接套上述聊天费率的 embedding/rerank 产品，因此不做这种假定。

中文字符换算只能估算，不能作为硬预算准确计数。官方页面给出的字符比例也注明与模型 tokenizer 有关、以 usage 为准；原文、工具 schema、时间/来源元数据、检索片段、图像与工具结果都可能占输入，不能只数用户说了多少字。[官方 Token 用量说明](https://api-docs.deepseek.com/quick_start/token_usage/)

### 6.3 价格快照与反直觉例子

以下来自 2026-10-26 查询到的官方人民币价格页，单位为元/百万 Token；不是本项目账单。页面显示 `deepseek-flash` 对应 Flash-1017，`deepseek-v4-pro` 对应 Pro-0813，均列 1M 上下文。高峰为北京时间工作日非中国法定节假日的 09:00–12:00、14:00–18:00，其余为空闲时段；上线应重新核对并保存价目版本。[官方模型与价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)

| 模型 | 缓存输入：空闲 / 高峰 | 未缓存输入：空闲 / 高峰 | 输出：空闲 / 高峰 |
|---|---:|---:|---:|
| deepseek-flash | 0.02 / 0.04 | 1 / 2 | 4 / 8 |
| deepseek-v4-pro | 0.15 / 0.30 | 4.5 / 9 | 13.5 / 27 |

**更少输入 Token 不必然更便宜。** 纯算术示例：使用上述 Flash 高峰价格，同样输出 500 Token；方案 A 输入 40,000，其中命中 39,000，费用为 `0.00156 + 0.002 + 0.004 = 0.00756 元`；方案 B 输入 8,000，但仅命中 2,000，费用为 `0.00008 + 0.012 + 0.004 = 0.01608 元`。B 的输入更短，却在这组假设下更贵；其额外抽取/检索费用尚未计入。这不是实测，也不是推荐全文历史，而是说明需要同时报原始 Token、命中率、总账单和答复质量。

缓存是已持久化前缀单元的完整匹配，属于 best-effort，不能保证每轮命中；它不是永久记忆。建议稳定的规则与人格前缀尽量稳定，动态时间、检索记忆放在合适的后续位置；但人工修订优先于保持缓存命中，不能为了省钱继续发送已撤销事实。改动请求前缀后，以实际 usage 验证效果，不沿用旧文档中的固定块大小经验。[当前缓存规则](https://api-docs.deepseek.com/guides/kv_cache/)

另一个容易漏掉的费用：官方页面说明 Search/Fetch 按成功请求计费，并公告相关 Server 端工具调用从北京时间 2026-11-01 起收费。因此 B站观察如经这些工具获取内容，成本不一定全在 Token 里；直接 B站请求则按实际所用数据源另计，不能混用价目。[官方 Search/Fetch 计费说明](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)

### 6.4 初版节流建议

- 用户明确管理记忆立即执行；普通聊天增量批处理，不逐轮重写全量人格/全生涯摘要。
- 检索先做身份、时间和状态过滤，再对少量候选按需重排；不默认每句问候都启用多轮 query expansion 与反思。
- 给前台聊天和后台观察/抽取分别设预算；后台预算不足暂停非紧急维护，并显示积压，不静默丢记忆，也不挤掉人工更正。
- 自主唤醒可做“什么也不说”的决策，但这轮仍可能收费；用产品规则先排除明显不该执行的活动。
- 新增 LLM 去重、反思或图谱维护前做消融。衡量每条有效记忆成本、每次有用召回成本和全生命周期成本，不只看回答时少了多少 Token。
- 原型可用固定请求上限与输出预留控制最坏情况；实际 usage 回来后结算，超时账目保留未知。不要未经测量就承诺精确到分的月消费。

## 7. 公平对照与评价方法

至少保留四条同底模基线，而不是把新系统与明显弱化的对照比较：

| 方案 | 允许使用的上下文 | 主要风险与要计入的费用 |
|---|---|---|
| A 全文历史 | 按时间排列、相同可用历史；放不下时明确标超窗/统一截断策略 | 输入长、位置效应；缓存可降低价格。超窗的 A 不能仍称“全文” |
| B 滚动摘要 | 固定预算摘要 + 相同近期窗口 | 漏细节、事实漂移；摘要构建与更新费用必须计入 |
| C 检索 | 相同原始来源，结构化过滤 + 选定检索器，固定注入预算 | 检索漏召回/错主体；建索引、embedding、重排均计入 |
| D 混合 | 权威事实/经历 + 原证据片段 + 相同近期窗口 + 可追溯摘要 | 多模块复杂度；维护与失效传播成本必须计入 |

两组评测都需要：一组固定回答上下文预算，另一组固定总生命周期成本，分别画质量—延迟—费用关系。底模具体版本、thinking 模式、生成上限、温度、工具权限、历史前缀、时间戳、询问顺序、缓存冷/热条件一致；明确各组构建阶段允许看见哪些历史，不能提前看到未来问题或修订。另设“只给正确证据”的 oracle 上界，用于分辨检索失败与读者理解失败。

指标至少分四层：

1. **存储与治理**：正确抽取率、错误主体/否定率、去重率、更新后旧值泄漏、人工更正传播延迟、已撤销来源重生率、任务崩溃恢复一致性。
2. **检索与上下文**：证据级 Recall@k / Precision@k、按 Token 预算的证据覆盖、时间/关系过滤错误、最终上下文中的正确证据覆盖。命中证据所在 Session 不等于命中所需事实。
3. **答复与关系体验**：事实/时间/来源正确性、该拒答时拒答、是否恰当地利用隐含线索；中文人评另看不机械复述、不无关翻旧账、不把推断说成事实、不冒认共同经历。记忆有效不一定要在答案里显式念出记忆。
4. **系统代价**：读取延迟 p50/p95、持久写入延迟、后台积压、全阶段 Token/金额、缓存命中、每次重建成本；评测 judge 的费用单列，不冒充用户运行费用。

LongMemEval 官方评测源码会在部分时间题容忍一天偏差，知识更新题中同时包含旧信息与正确新值也可能判对；这种得分不足以证明产品严格遵守“不要再提旧地址”。应保留原 benchmark 可比结果，再加自己的严格治理判分，不能修改官方 judge 后继续冒用原指标名称。[作者评测代码，固定提交 9e0b455f](https://github.com/xiaowu0162/LongMemEval/blob/9e0b455f4ef0e2ab8f2e582289761153549043fc/src/evaluation/evaluate_qa.py)

建议先构造人工可审阅的中文虚构关系数据，覆盖口语、昵称、否定、省略、转述、跨日时区和隐含提示；开发集与最终验收集隔离。再使用获得授权的真实样本。重复随机运行并报告逐题结果及置信区间；LLM judge 与人工抽检并用，删除/重启等系统断言不交给“看起来像成功”的文本评委。本文没有运行上述对照。

## 8. 15 个必须有的验收场景

下面的“通过”是拟定验收条件，不是已通过记录。对明确禁止使用、跨关系混淆和撤销竞态，验收样例中的违规数应为 0；这只是该样例集门槛，不是普遍零错误保证。

| # | 场景与操作 | 需要验证的结果 |
|---|---|---|
| 1 | 先说“朋友喜欢猫，我更喜欢狗”，之后询问偏好 | 主体归属正确；不能因句子相邻把朋友偏好写给主人；返回可定位证据 |
| 2 | “以前喜欢甜的，最近改喝无糖” | 回答当前偏好用新值，询问过去时能识别旧时间范围；不简单删除真实历史 |
| 3 | 用户明确更正“上次日期写错了”且锁定新值，随后重放旧聊天 | 旧来源不覆盖人工修订；冲突/审计可查；后台摘要、索引和生成只用允许版本 |
| 4 | “今天很难过”，一周后正常聊天 | 临时状态按时效处理，不自动推断永久性格/诊断，也不每次无关追问 |
| 5 | 多天分散说明称呼和沟通偏好，后来只说“又要做那个汇报了” | 能从隐含线索召回必要背景；不要求用户重复全部设定，也不过度暴露无关隐私 |
| 6 | 同一事实被 QQ 重投、导入和摘要引用；另有不同天两次真实活动 | 前者不重复加权/写多条，后者不被误合并；来源与独立事件数准确 |
| 7 | 多轮压缩包含否定、条件、日期和昵称的历史 | 摘要关键断言可回溯原文；无法支持的推断不能进入事实层；与原证据读取对照 |
| 8 | 两条关系/两个用户出现相同昵称和相似经历 | 召回、摘要、图谱和回复均不跨 relationship；测试别名变化不破坏绑定 |
| 9 | B站视频说“大家都该早起”，主人说“不适合我”；只有标题读取成功 | 外部观点与主人偏好分开；不得记录主人赞同、不得宣称看完视频 |
| 10 | 删除某记忆时，旧摘要/embedding任务已开始但尚未提交 | 删除事务完成后旧任务不能写回；旧候选不进入上下文或 QQ 出站；有可核对 epoch |
| 11 | 禁用来源后重启、重建索引、从较旧备份恢复 | 撤销规则先于重建生效；来源及其派生材料不再学习。无法确认撤销版本时不自动恢复使用 |
| 12 | 遗忘触发 Session 轮换，但旧 Schedule 已到期或重投 | 旧会话代次不再处理记忆/工具/外发；旧任务对账完成，新任务不会双触发 |
| 13 | Agent 生成分享候选并写入日志，发送前人工修订；另一次发送超时 | 失效候选不被当成已经说过；超时保持 unknown，人工关重试不把它改成“确定没发” |
| 14 | 询问从未告诉过的生日/共同经历；或反事实“假如我去东京” | 拒绝编造、不冒认经历；必要时澄清。问答准确率与恰当拒答分开计分 |
| 15 | 在相同历史/提问上跑 A/B/C/D，含冷缓存、热缓存、流式中断和后台维护 | 报告全阶段 Token/费用/延迟与质量；缺 usage 不记零；余额、预算与上下文空间显示分开 |

## 9. 进入实现前的最小决定

首版把努力放在：**来源与主体归属、当前/历史版本、人工锁定与撤销、可重建派生材料、原证据召回、全阶段成本账本和上述验收**。不需要先建复杂图数据库或让模型自主改写所有记忆。先验证混合方案是否优于全文/摘要基线，再决定增加语义模型、重排、图关联或更频繁反思。

本轮来源验证截至 2026-10-26；价格、模型别名和服务端缓存规则会变化，部署前需重查。论文结果只作方法证据，未被转换成本产品的实测指标或稳定性承诺。
