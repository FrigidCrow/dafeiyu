## 第一轮执行顺序与判据

1. **固定实验版本并启动 DSH。** 依据源码报告选择可复现版本，记录版本和来源；确认原型使用真实 DSH 执行、会话、工具和上下文机制，而不是自己写一个模型循环替代它。报告中的版本是研究基线，不自动代表当前发布版或已兼容组合。
2. **接入最小陪伴模块与简易管理页。** 使用虚构样本，证明页面修改人格、记忆和预算后，实际 DSH 请求使用同一份最新有效状态；展示保存结果及实际送给模型的相关内容。页面能展示按钮或更新自身状态不算接入通过。
3. **演练记忆生命周期。** 从已引用的验收场景中取一条：形成记忆 → 人工纠正 → 遗忘 → 下一轮交流 → 压缩/新会话 → 重启 → 尝试读取旧来源。观察当前输入、摘要和后续整理是否仍遵守有效状态；必须暴露失败路径，不能仅凭一句回答宣称已经遗忘。
4. **验证预算确实约束运行。** 先用已知的模拟用量观察状态和停止发起请求的行为；真实调用时再核对服务商 usage。统计覆盖范围与不能取得的数据须明示，不能用页面显示的数字替代计费证据。
5. **给出判定。** 分别报告“状态演示”“真实 DSH 接入”“真实模型行为”“重启恢复”哪些通过、失败或未运行。通过第一轮才扩展真实 QQ 与 B站链路；失败则指出具体能力缺口和适配成本，不擅自把框架切换为 AstrBot。

本轮不需要先锁定某个长期记忆库，也不要求完成正式管理后台。实验状态应使用明显标识的样本与临时存储；本题明确需要验证持久化，因此可使用 scratch 数据文件，不能把生产数据作为试验材料。
